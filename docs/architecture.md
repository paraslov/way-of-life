# Way of Life — архитектурные концепции

Общий справочник для всех планов этапов. Если план этапа противоречит этому документу,
прав этот документ, пока в [журнал решений](./way-of-life-plan.md#журнал-решений) не записано другое.
Продуктовая модель и принципы — [мастер-план → Модель](./way-of-life-plan.md#модель-философия-v1)
и [concept-plan.md](./concept-plan.md); здесь — как они реализуются.

Последнее обновление: 30.09.2026

---

## 1. Четыре закона

1. **Правильная точка сравнения.** Носимые сигналы (сон, RHR, HRV) сравниваем с личным
   baseline, абсолютные числа нужны только на старте. Маркеры риска (давление, липиды, HbA1c,
   талия) — с клиническими ориентирами и собственным трендом (D23).
2. **Adherence > идеальная программа.** Ввод данных не должен становиться второй работой.
3. **Решение, а не отчёт.** Каждый экран отвечает на вопрос «что делать».
4. **Наблюдения храним навсегда, интерпретации можем менять.**

## 2. Три слоя: наблюдение → интерпретация → решение

```text
OBSERVATION        INTERPRETATION             DECISION
sleep_minutes=342  → sleep: RED (правила v1)  → Порог → лёгкий бег 35 мин
rhr=57, base=52    → rhr: YELLOW              → выбрано: «принять»
```

- **Наблюдения** — сырые факты в таблицах. Их никогда не перезаписывает логика.
- **Интерпретация** — чистые функции в `src/lib/*` (сигналы, baseline, агрегаты). Результаты
  вычисляются при чтении и в таблицы не записываются.
- **Решение** записывается в `day_decisions` вместе с `rule_version` и `snapshot` (jsonb:
  входы, baseline, сигналы). Тогда потом можно сказать: «28.09 приложение рекомендовало
  восстановление по правилам v1.3».
- Правила версионируются константой `RULES_VERSION` в коде. Если правила меняются,
  прошлые решения остаются как есть, а графики пересчитываются по новым правилам.
- **Отсутствие данных — не наблюдение.** Пустое поле хранится как `NULL` и даёт `UNKNOWN`,
  а не ноль, «плохо» или отдых. Производные значения всегда можно пересчитать из наблюдений.

### Жизненный цикл решения дня (D25)

- **День открыт** (сегодня в часовом поясе пользователя). Сохранение утреннего чек-ина
  пересчитывает светофор и рекомендацию в той же транзакции. Изменившаяся рекомендация
  сбрасывает выбор: он отвечал на другой вопрос. Выбор можно менять весь день.
- **Вечер.** Вечерняя запись фиксирует, чем день закончился: активности, «как легло решение»,
  спокойствие. `day_decisions` она не меняет.
- **Конец локального дня** — решение окончательно, журнал показывает сохранённый `snapshot`.
- **Дописать прошлый день** (D27) можно 7 дней: из журнала или недели открывается модалка с
  утром, активностями и вечером. Наблюдения пишутся на дату того дня, `day_decisions` не
  пересчитываются и задним числом не создаются. Красные флаги прошлого утра не меняются
  (они для действия «сейчас»). Утро, введённое после конца дня, помечается
  `daily_checkins.late_edited_at`. Журнал показывает вердикт по текущим правилам: для дня
  без решения — вместо решения («заполнено позже»), для дня с решением — рядом с ним.
  Старше 7 дней — только чтение.

## 3. Реестр показателей (metric registry)

Метаданные показателей живут **в коде** (`src/lib/metrics/registry.ts`), а не в таблице
базы. EAV для всего подряд не делаем.

```ts
{ key: "sleep.duration", name: "Сон", unit: "min", domain: "recovery",
  frequency: "daily", sources: ["manual", "garmin"],
  baseline: { strategy: "mean", windowDays: [7, 30] }, signal: sleepSignal }
```

- Домены: `recovery`, `aerobic`, `strength`, `mobility`, `body`, `medical`, `habits`, `subjective`.
- **Ось** (`capacity` | `vitality` | `risk`) — одна основная на показатель (D22): максимум
  возможностей → `capacity`, текущее состояние и симптомы → `vitality`, структурный или
  долгосрочный процесс → `risk`. Домен группирует хранение и справочник, ось — интерпретацию
  и экраны. Поле `axis` добавить в реестр в 04.1.
- **Типизированные таблицы** для частых данных (чек-ин, тренировки, подходы) и **одна
  таблица `measurements`** для редких (тесты, талия, VO₂max, давление). Её строки ссылаются
  на `metric_key` из реестра.
- Анализы лежат в отдельной таблице `lab_results`: у них свои единицы и референсы (см. §7).
- Вечерние наблюдения — прогулки после еды, белок и клетчатка диапазонами, отбой, оценка
  решения, спокойствие за день — лежат в `day_evenings`, одна строка на день (02b, D26).
- Этап 03 показывает все виды движения в «Активностях»: выполненная сессия остаётся одной
  записью в `activities`, детали упражнений ссылаются на неё. Вариант сессии отделён от
  широкого `type`; «Сегодня», «Неделя», «Журнал» и «Активности» читают общий факт (D21).

## 4. Происхождение данных (provenance) и дедупликация

У каждого наблюдения есть `source` (`manual` | `garmin` | `lab` | `test` | `cpet` | …),
а при необходимости ещё `method`, `device` и `note`.

- VO₂max по оценке Garmin и VO₂max по CPET — **разные** наблюдения одного показателя.
- LTHR от автоопределения Garmin и LTHR из 30-минутного теста различаются по `method`.
- Ручной ввод с первого дня пишется с `source = 'manual'`.

### Каноническое хранение (D24)

**Основной путь — ручной ввод.** Garmin опционален: импорт читает файл одной активности,
забирает нужные значения и не сохраняет сам файл. Сон, RHR и HRV вводятся руками и не
обязательно каждый день; их импорт не планируется, пока гейт не покажет, что ручной ввод
главный раздражитель.

| Наблюдение | Где живёт | Источник |
|---|---|---|
| сон, Sleep Score, RHR, HRV (мс и статус) | `daily_checkins` | manual, по желанию |
| энергия, желание двигаться, ноги, шаги, красные флаги | `daily_checkins` | manual |
| симптомы | `symptom_entries` | manual |
| вечер: прогулки, белок, клетчатка, отбой, оценка решения, спокойствие | `day_evenings` | manual |
| выполненная активность, в том числе контрольная (§11) | `activities` + детали 03 | manual или файл Garmin |
| редкие измерения: вес, талия, давление, VO₂max, тесты | `measurements` (04) | manual / garmin / cpet / test |
| анализы | `lab_results` (06) | lab |
| решение дня | `day_decisions` | вычисляется, окончательно в конце дня (§2) |

- У каждого наблюдения одно место. Импорт не создаёт вторую серию: он создаёт или дополняет
  ту же запись после предпросмотра.
- `daily_checkins` — одна строка на день, `source` у неё всегда `manual`.
- Для активностей `UNIQUE (user_id, source, external_id)` защищает от повторного импорта
  одного файла. `external_id` — id активности Garmin или хеш файла. Если в этот день уже есть
  ручная запись того же вида, импорт предлагает дополнить её, а не создать вторую; обе по
  умолчанию не считаются.
- Сырые данные файла не хранятся: пользователь видит извлечённые значения, правит их в
  предпросмотре, и сохранённое становится каноническим. Отдельная сущность `import_batch`
  не нужна, пока импорт — одна активность за раз: откат = удаление этой активности.

## 5. Baseline engine

Отдельный модуль `src/lib/baseline/`, чистые функции с юнит-тестами.

```ts
baseline(series, { strategy: "median" | "mean", windowDays, minPoints, excludeToday })
  → { value, band: [low, high], n } | null
```

| Показатель | Стратегия |
|---|---|
| RHR | медиана, 28 дней |
| HRV | медиана, 28 дней, коридор — статус Garmin, если введён |
| Сон | среднее, 7 и 30 дней |
| Энергия | медиана, 14 дней |

Если точек меньше `minPoints`, функция возвращает `null`. Сигнал тогда строится по стартовым
абсолютным порогам из плана v6 и помечается «по стартовым порогам».

- **Два уровня качества:** стартовый (из `defaults`, пока `n < minPoints`) и личный
  (`n ≥ minPoints`). Интерфейс честно пишет, какой действует: «по стартовым порогам» или
  «медиана за 28 дней, n = 23». Промежуточный уровень «provisional» не вводим: `n` и окно
  уже показывают, насколько baseline надёжен.
- **Редкие данные — норма.** Сон и HRV не обязательно вводить каждый день: окно считает
  доступные точки, пропуск не равен плохому значению и не прерывает окно.
- Baseline относится только к носимым сигналам и самооценкам. Маркеры риска интерпретируются
  относительно клинических ориентиров и тренда (§1).

## 6. Светофор

- Светофор описывает **режим ресурса дня**, а не разрешение тренироваться: GREEN — обычный
  день, YELLOW — уменьшить необязательную нагрузку, RED — приоритет восстановления. Подмена
  тренировки — первый use case. В V0.2 `recommended_action` — тренировочное действие, но
  схема и код не должны закреплять «действие дня = тренировка»: позже им может стать сон,
  прогулка или медицинская задача.
- Состояния: **GREEN · YELLOW · RED · UNKNOWN**. Если данных нет, это `UNKNOWN`, а не плохой сигнал.
- Итог считается по худшему **известному** сигналу. Один жёлтый при остальных зелёных
  не учитывается, но показывается. Если все сигналы `UNKNOWN`, итог `UNKNOWN` и действует план по умолчанию.
- **Никакого итогового score** вроде «Readiness 83 %». Показываем вердикт, объяснение
  по каждому сигналу и действие.
- Красные флаги (перебои не проходят на шаге, боль в груди, предобморок, одышка не
  по нагрузке) идут **вне светофора**: они перекрывают любое решение.
- **HRV — одна интерпретация.** В v1 сигнал светофора — статус Garmin, введённый руками
  (интерпретация Garmin, так и подписана). `hrv_ms` хранится как сырое наблюдение, но в v1
  не интерпретируется. Собственный сигнал от baseline `hrv_ms` появится не раньше гейта и
  при n ≥ 14. Тогда он станет основным, а статус Garmin — контекстом. Оба в вердикт
  одновременно не голосуют.
- Решение дня состоит из двух полей: `recommended_action` от приложения и `chosen_action` от
  пользователя (`accept` | `keep_original` | `skip` | `custom`). Так замыкается петля
  N=1-обучения.

## 7. Единицы, референсы, время

- **Единицы.** У каждого показателя в реестре есть каноническая единица, значение хранится
  в ней. Анализы — исключение: храним **как напечатано** (`value`, `unit`, `ref_low`,
  `ref_high`, `ref_text`, `lab`). Глобальных «норм АЛТ» нет.
- **Время.** В `user_settings.timezone` по умолчанию `Asia/Almaty`. Дневные сущности
  используют ключ `local_date date`, события хранятся как `timestamptz` (UTC). Сон относится
  к дате пробуждения. «Сегодня» всегда вычисляется в часовом поясе пользователя
  (в ACT уже есть этот паттерн: `event_timezone`, `timezone-switcher`).

## 8. Конфигурация вместо хардкода

- **Targets** хранятся в таблице `targets`: `metric_key`, `period` (`day` | `week`), `minimum`,
  `target_min`, `target_max`, `active_from`. Начальные значения записываются из плана v6.
  Экран «Неделя» агрегирует targets автоматически, а не собирается вручную.
- **Семантика доз — `minimum / target / optional`** (D22). `minimum` — достаточно для
  плохой недели, `target_min…target_max` — хорошая обычная неделя, **optional** — всё сверх
  `target_max`. Optional не хранится отдельной колонкой: это правило «только при ресурсе».
  Сверх нормы показывается нейтрально, без похвалы, и не рекомендуется в жёлтый или красный день.
- **Generic и typed targets.** Скалярные суммы и средние (аэробные минуты, шаги, сон, белок,
  клетчатка, сессии подвижности) агрегирует общий движок. Составные цели считают отдельные
  функции в `src/lib/week/`:
  - силовая: minimum = 1 полная + 1 Lite, target = 2 полные; Lite не заменяет полную;
  - интенсивная: правило частоты «1 раз в 7–10 дней», а не недельная цель; после 7 дней —
    «снова доступна», без «просрочена»;
  - мощность/баланс: сессии × минимальная длительность;
  - дни отдыха: только явная отметка (ниже).

  Сейчас код упрощает силовую до minimum 1 и интенсивную до «1 в неделю» (`src/lib/seed.ts`).
  Заменить при реализации 03/05.4. Универсальный DSL и EAV не строим.
- **Отдых ≠ отсутствие данных.** День отдыха засчитывается только по явной отметке «Отдых».
  Прошедший день без записей — «нет данных». Дни болезни, поездки, обострения и травмы —
  дни режима (ниже): не отдых и не провал. Отметка «Отдых» в день с тренировкой отдыхом
  не считается.
- **Режимы — периоды, а не свойство недели.** Сейчас это `week_modes` на неделю (`normal` |
  `deload` | `travel` | `illness`). Цель — период с датами начала и конца: `illness` (с
  отметкой «была температура»), `travel`, `flare` (обострение ЖКТ), `injury` (что болит),
  `deload`. Во время периода недобор targets нейтрален и действует minimum режима,
  рекомендация учитывает режим, quality не предлагается. После периода действует
  **протокол возвращения** из [rules-v1.md](./content/rules-v1.md#режимы-и-протоколы-возвращения).
  Числа протоколов — в контенте, а не в коде. Сущность Plans/Protocols по-прежнему не нужна
  (D9): период плюс правила протокола покрывают сценарий.
- LTHR, зоны, HRmax, вес и цель по белку хранятся в `user_settings`, а не в коде.
- **Настройки, которые интерпретируют историю** (LTHR, HRmax, зоны, стартовый baseline RHR),
  действуют с даты. Решение дня хранит нужные значения в `snapshot` (например, потолок
  пульса 151). Когда прошлые активности начнут показываться в зонах (03), у настроек появится
  история с `active_from`, и прошлая дата читается по значению, действовавшему тогда. Новый
  LTHR не переписывает старые тренировки. Сырые значения (средний пульс, темп) от настроек
  не зависят.

## 9. Симптомы

Колонки под каждый симптом не заводим.

- `symptom_definitions`: `key`, `name`, `scale` (0–10 | да/нет), `pinned`, `archived`.
- `symptom_entries`: `local_date`, `symptom_id`, `severity`, `context`, `note`.
- В чек-ине видны только закреплённые симптомы (колено, бедро, перебои), остальные
  добавляются через «+ симптом». В начальные данные входят: колено, бедро (rectus femoris),
  перебои (+ ЧСС), рефлюкс, живот, икра.

## 10. Приватность и безопасность

Здесь хранятся медицинские данные, поэтому требования строже, чем в ACT.

- Приложение однопользовательское: без регистрации и инвайтов, пользователь создаётся через CLI.
- RLS на всех пользовательских таблицах, runtime-роль без `BYPASSRLS` (паттерн ACT).
- **Не логировать данные о здоровье.** Никаких `console.log(checkin)`, только логгер
  с белым списком полей. В CI добавить проверку на `console.*` в `src/`.
- Никаких analytics/telemetry SDK. Медицинских значений нет в URL и query string.
- Секреты только на сервере, cookie `Secure`, `HttpOnly`, `SameSite=Lax`, security headers.
- Бэкапы: PITR у Neon плюс `pnpm db:backup` — дамп на собственную машину в
  `~/way_of_life/backups` ([backups.md](./backups.md), D17). В облака дампы не уходят.
- Экспорт всех данных (JSON и CSV) и удаление всех данных — функции в настройках.
- Медицинские документы (файлы) появятся позже, только в приватном хранилище с
  подписанными URL.

## 11. Контрольные сессии (D24)

Прогресс аэробного резерва виден не по одной тренировке, а по **повторяемым контрольным
сессиям** с одинаковым протоколом. Пример: в сентябре лёгкий бег 5 км — темп 7:12, средний
пульс 138; в декабре тот же протокол — 7:03 и 133. Темп чуть выше, а главное — на той же
нагрузке упал пульс.

- Контрольная сессия — обычная запись в `activities` с отметкой «контрольная» и
  `protocol_key`: вариант и условия, например `run.recovery.5k` (light, Z1), `run.easy.5k` (Z2), `run.tempo.*`,
  `run.threshold.*`, `run.4x4`, `hike.<маршрут>`. Точный словарь — в 03.1. Второй таблицы
  тренировок нет.
- Поля: дата, дистанция, время → темп, средний пульс; по желанию макс. пульс, набор высоты,
  RPE, условия (жара, ветер, рельеф). Для интервалов и темповых отрезков — значения рабочих
  отрезков: средний пульс всей интервальной сессии качество отрезков не описывает.
- Ввод руками или из файла Garmin одной активности (09): файл читается в памяти, извлекаются
  сводка и отрезки (laps), сам файл не сохраняется.
- Сравнивать можно только внутри одного `protocol_key`. Показываются темп и пульс вместе.
  Главный сигнал для лёгкого бега — пульс при том же темпе/усилии или темп при том же пульсе.
  Если условия заметно отличаются, сравнение показывается с оговоркой, а не как прогресс.
- Ось — Capacity, функция Горизонта — «4 этажа без остановки» и «неровная тропа».
  Отдельный score формы не строим, сырые значения от LTHR не зависят (§8).
